# DTQEight/basketball-clipper
一句话定位：固定机位篮球录像进球检测+自动剪辑（diff 帧差高召回 + YOLO 硬否决双通道，NiceGUI 界面）｜ stars：2 ｜ 语言：Python ｜ 最后更新：2026-09-06

规模：~6800 行（tracker.py 764 / services/detection.py 1935 / demo_nicegui.py 1691 等），文档极全（ALGORITHM/BENCHMARKS/CHANGELOG/FAQ/TRAINING）。

## 进球判定技术路线（重点）

双通道结构：**diff 帧差生成高召回候选 + YOLO 硬否决**。

### 检测器（diff 通道，tracker.py GoalDetector）
1. 标定时取无球帧为基准帧，只存篮筐搜索区（筐外扩 80px）的 ROI 灰度高斯模糊图（`tracker.py:175-203`）。
2. 每帧 ROI 灰度 → `absdiff(基准)` → 二值化。**自适应阈值**：前 30s 预热逐帧收集 diff 的 P95（降采样 1/16），结束取 `median(P95)+8`，clamp [8,50]；预热期只采样不判定（`tracker.py:253-257, 394-414`）。
3. 形态学 open+close（5x5 椭圆 kernel 缓存）→ findContours → 斑块过滤：面积 [30,5000]、宽 ≤1.5 倍筐宽、**圆度 4πA/P² ≥0.35**（滤长条人体）→ 取最大面积斑块（`tracker.py:225-312`）。
4. **滚动基准帧**：每 60s 或「斑块持续 >5s（球员常驻篮下）」触发更新；更新窗口内持续记录 diff-ratio 最小的帧作候选（避免把球拍进基准），只存 ROI 灰度 ~90KB（`tracker.py:416-449`）。

### 判定逻辑（状态机，tracker.py:477-583）
- 斑块中心位置分三段：上方（y<筐上沿）/ 框内（y 在框带且 x 进筐 ±30% 框宽）/ 下方（y>筐下沿）。
- 三条进球路径：
  - **visual**：上方→下方穿越（1.5s 超时窗口允许中间漏检几帧）；
  - **side**：框内出现 ≥1 帧后到下方（侧向进筐，不要求先到上方）；
  - **loose**：宽松模式进框连续 ≥2 帧即候选（约 0.07s@30fps）。
- 附加校验：in_x（x 在筐 ±30% 宽内）、size（斑块宽 ≤1.2 筐宽）、**下落趋势**（最近 4 帧 y 位移 >5px，`tracker.py:603-612`）。
- 冷却 3s 防重复计数。
- 诊断计数器 `diag`（reject_in_x/reject_shape/reject_trend/yolo_rejected 等 19 项，`tracker.py:156-173`）用于调参排查。

### YOLO 通道（否决器，非主检测）
- 检测循环里每 2 帧（提速模式每 3 帧）跑一次 YOLO；篮筐区无运动像素（1ms 快检，运动像素比 ≤1%）时**条件跳过**，实测跳过率 94%（`services/detection.py:580-597`、`tracker.py:205-223`）。
- 权重：`weights/basketball_custom.pt`（自训，仓库不含）回退 COCO yolov8n；**按 model.names 反查球类索引**（自定义=[0] basketball，COCO=[32] sports ball），防把 person 当球（`app.py:78-124`）。conf=0.3，imgsz=960。
- **硬否决规则**：候选注册进球时，检查 YOLO 球位置历史（±0.34s ≈10 帧窗口）中筐 ±1 倍宽高范围内是否有球，无球直接拒绝（`tracker.py:614-631, 501-517`）。跳帧复用上一帧 YOLO 结果但保留原始检测帧号。

### 误报控制手段
圆度过滤人体 + 面积/宽度上下限 + 下落趋势 + 冷却 + YOLO 硬否决。FAQ 称 1st.mp4 误检 183→32（硬否决贡献）；但 BENCHMARKS 承认 4th.mp4 漏 4 球（10.8%），「很可能全部是真实进球被 YOLO 硬否决误杀」。

## 出手人/球员识别
无 CV 自动识别。**全人工归人 UI**：进球卡片点 👤 弹对话框 → 本场已用人名（彩色徽章）+ 全局名单（persons.json，跨场次复用）+ 输入新人名；按人物筛选导出个人集锦 `{视频名}-{人物}-highlights.mp4`（`demo_nicegui.py:1088-1170`、`services/detection.py:986-1128`）。人物配色按名字排序循环取调色板保证同屏不撞色。

## 工程亮点
- **断点续跑**：每 300 帧 checkpoint，完整序列化检测器动态状态（含基准帧/滚动候选帧 PNG-base64、预热 P95 样本列表、YOLO 球位置历史、diag 计数），恢复跳过预热（`tracker.py:633-764`）。
- PyAV 视频读取：HEVC / moov 后置 / NAL 损坏逐包跳过容错（`video_io.py`）。
- 剪辑 NVENC 硬编探测（h264_nvenc cq=20）回退 libx264 crf=18（`cutter/ffmpeg_cutter.py`）。
- **标签飞轮**：√/× 人工标记增量写 `labels.kept / deleted`（时间戳集合）+ `labels.persons` + label_time，持久化到每视频 JSON（`services/state.py:682-731`）；重跑后标签按时间戳容差重映射到新 goals（`_remap_labels_to_goals`）。README 称「训练池直通标签飞轮」，但训练/标注工具（label_tool.py、auto_train.py）已从仓库删除，只剩 git 历史（`doc/TRAINING.md`）。
- YOLO 故障熔断（失败率 ≥50% 提前中止防空跑）、模型负缓存、CUDA 主线程预热防崩溃、每 500 帧 empty_cache。
- ROI 先裁再处理（省 ~95% 计算）、fps 归一化防御 + 按秒定义的时间窗口按 fps 换算（防 60/15fps 失配）。

## 对我们项目的可借鉴点

痛点①（进球判定 FP）：
1. **「宽规则候选 + 检测器否决」漏斗结构被验证有效**（误检 183→32）：我们 HSV 规则层 ≈ 他们的 diff 层，已设计的穿越窗 crop + 小 CNN 可作否决器/确认器。但他们的教训（硬否决误杀 10.8%）直接支持我们用 **CNN 软打分 + 阈值** 而非硬否决——参考 `tracker.py:614-631` 的否决窗口设计（±1 筐宽高 × ±0.34s）和 `services/detection.py` 的 YOLO 跳帧+运动门控调度（若 CNN 推理贵，同款「无运动不推理」门控可移植）。
2. **自适应阈值（30s 预热 P95 中位数）**：我们 HSV 阈值目前手工调；同思路可对整场 diff/HSV 信号做分布自适应，缓解场次光照差异。
3. **滚动基准帧**（60s 最小运动帧 + 球员常驻触发）：他们解决长视频光线渐变/人员滞留的方案；我们 ORB 解决的是碰移位，两者正交，若我们引入任何背景差分可复用。
4. **diag 诊断计数器分类拒绝原因**：调参时直接看「哪条规则杀了多少候选」，与我们 truth/ 回放标定指纹思路互补，成本低收益高。

痛点②（出手人归人）：
5. 他们也没解决自动归人——最成熟的一家仍是全人工，但做了三个降摩擦设计可抄：**全局人物名单跨场次复用**（persons.json）、**彩色徽章同屏辨人**、**按人导出集锦**。我们的墙+人工归人可补「名单复用」和「按人导出」。
6. **labels.kept/deleted 时间戳标签池 + 重跑重映射**：与「335 事件真值做 CNN 训练集」完全同构——每次人工 √/× 自动沉淀训练数据，且重跑检测后标签按时间戳容差自动转移到新结果，避免重标。建议我们在 CNN 落地前就把标签存储做成这种增量飞轮格式。

## 明确不适用的点及原因
1. **目标尺度不匹配**：他们的筐 84×84px@1080p（BENCHMARKS 坐标 331,239-415,323），我们 35-65px；YOLO imgsz=960 对我们小球的检出率未知，硬否决在小目标上漏检风险被放大（他们大目标都误杀 4 球）。
2. **帧差检测的是「运动物体」而非「橙色球」**：他们靠圆度滤人，我们靠 HSV 滤色——他们的人肤/同色混淆问题我们不存在，反之他们的多人持续移动场景靠面积+圆度能扛是因为球在筐边运动最显著；直接换帧差会引入新的 FP 面（我们已证伪过颜色之外的路）。
3. GPU 硬性要求（无 CPU 降级）与我们轻量本地部署不符。
4. 前提「固定机位标定后基准稳定」——我们偶尔被碰移位，靠 ORB 而非滚动基准解决，两个机制不能混用（滚动基准会把移位后的帧当新基准，静默吞掉偏移）。
