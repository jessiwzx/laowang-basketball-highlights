# Shahzad-Khan9294/RealTime_MultiAngle_Goal-Miss_Detection-Basketball_VideoAnalytics
一句话定位：**两级 EfficientDet-Lite 的进球检测 demo**（筐区 ROI 裁剪 → 在裁剪帧上直接检测"goal"外观），疑似 Ballogy 公司招聘测试题作品 ｜ stars: 0 ｜ 语言: Jupyter Notebook+Python ｜ 最后更新: 2025-09-07（创建次日即停，1 个 commit）

## 核心技术路线（goal/miss 分类）
**无轨迹分析（描述里写了 trajectory analysis 但代码里没有）、无时序逻辑，纯"外观检测"两段式：**

1. **第一级：找筐定 ROI**（ROI_Basket.py）。TFLite EfficientDet（两类 `['ball','net']`）在视频前 300 帧内检测 net，取第一个命中帧的 net 框，外扩成静态 ROI（左右各 +0.6~0.8 倍宽、上 +1.6~1.8 倍高、下边不动），然后**整个视频按此固定 ROI 裁剪成 jpg 序列**（notebook 版裁成视频）。ROI_Basket.py L72-75。
2. **第二级：ROI 帧上检测"goal"**（Goal_Detection.py）。单类 `['goal']` 的 EfficientDet-Lite 逐帧推理（阈值代码里 0.2，README 说 0.7 才理想），画框输出。**"goal"这个类学的就是"球在网里/穿网瞬间"的外观**——结果图（Output_Result_Images/bb_ss1.JPG，11 帧序列）证实：球进网前无框，球在网中的连续帧在网部出框，球掉出后消失。
3. **多角度策略**：按机位分别训练 central_angle / score_side 两个专用模型 + 一个全角度混合模型 mixed_model2_1（Fine_Tined_TFLite_Models-EffDet/ 下 3 个 4.4MB tflite，EfficientDet-Lite0 量级、TFLite Model Maker 风格输出 output_0~3）；README 结论是混合模型跨视角更稳，代码实际默认用混合模型（Goal_Detection.py L100）。
4. 模型与训练代码**不在仓库**（无训练脚本/数据集/评估脚本），只有 3 个 tflite 权重文件。

## 对我们项目的可借鉴点（痛点①进球判定）
1. **路线级印证——这是对我们 CNN 方案最有价值的旁证**：它把进球判定从"轨迹+几何判据"换成"在筐口邻域裁剪图上直接检测进球外观"，恰好就是我们已设计未实施的「穿越窗帧 crop + 小 CNN」同构方案。它用 EfficientDet-Lite0（4.4MB）就能在干净测试集上到 98%，说明**该问题对外观模型是可学的**，我们的 335 事件真值足够支撑同类小模型。
2. **ROI 外扩参数可参考**：以网为锚，左右各 +0.6~0.8 倍宽、上方 +1.6~1.8 倍高、下方不扩——即"进球判定的观察窗=网口上方一个球道漏斗"，与我们穿越窗 crop 的取窗直觉一致，可作超参起点。
3. **按机位分模型 vs 混合模型**：它结论是混合模型更稳。我们固定机位（偶尔移位）场景应训单一模型+移位后重标定即可，比它更简单。
4. **"球在网中连续帧"作为事件核心证据**：结果图显示 goal 检测在连续 7 帧上稳定出框——提示我们的 CNN 判据也应做成"窗口内多帧投票"而非单帧判定，与既有下落校验/实体再现校验的时序思路吻合。
5. 反面教训：**静态 ROI 在镜头被碰移位时会整体失效**（它没有任何应对）——印证我们 ORB 配准的必要性，CNN 方案里 crop 窗也必须跟随配准后的筐口位置。

## 明确不适用的点及原因
1. 98% 指标不可信、不可复现（无训练/评估代码）；其测试视频是室内近距大筐画面（篮板占屏幅很大），与我们 35~65px 小筐、人群遮挡的野球场景难度不可比。
2. 无 miss 判定细节：miss=没检测到 goal，对它够用；我们需要区分"没进"与"没看到"，其方案无参考价值。
3. 无出手人、无轨迹、无剪辑/统计功能，与我们的归人痛点无关。
4. 代码质量低（未跑通的脚本、阈值矛盾），任何具体实现细节不值得照搬，只有路线思想可取。
