## 数据集与权重（重点：类别/规模/格式/获取途径/训练来源）

- **仓库内无数据集、无权重、无代码**：39 个文件全是 .md 与 .png。
- 唯一可信口径（1.0_datasets.md）：**BasketBall_Game 数据集，714 张，640×640，YOLOv8 格式，CC BY 4.0，6 类 = basketball / made(命中) / player / ref(裁判) / rim / shoot(投篮动作)**。仓库里多张 `*_jpg.rf.<hash>_effect.png` 文件名是 Roboflow 导出命名法——即底层是 Roboflow Universe 公开数据集的下载/标注可视化。看图确认：**室外野球场（围栏+塑胶地）、边线手持/固定机位、小目标**（player 框约 30×140、ball/rim 框 50~80px/640 宽图）——与我们的场景同类。
- readme.md 其余章节的数据集口径互相矛盾：1.4.1 称「1000 段视频、4 类目标+4 类动作（8.5k 球员/6.2k 球框）」；2.4 称「100 场职业比赛、ball 平均 16×16 / rim 平均 24×24」——同一仓库三套数字，AI 生成痕迹明显，皆不可采信，实验表大概率是编造的。
- 获取途径：代码/数据集/权重号称开源，实际全部指向 kdocs.cn（金山文档 `kdocs.cn/l/cszuIiCKVNis`）与 bilibili 空间引流页，仓库本身拿不到任何资产。

## 检测/识别技术路线（含动作识别）

- 声称路线：VanillaNet-5 极简骨干替换 CSPDarknet + 注意力 + 多尺度训练，配 YOLOv8 检测头；文档内容基本是 VanillaNet 论文复述（2.3_VanillaNet网络结构.md、4.2_改进后的后端算法.md 里贴的是论文级示意代码，非可运行工程）。
- **动作识别的真实口径 = 把动作当检测类别**：数据集里 shoot/made 本身就是包围盒类别；readme 2.5.2 称「添加了一个简单的分类分支」识别投篮/运球/传球/防守。无时序建模、无跟踪器（ByteTrack/DeepSort/光流只出现在「未来工作」和 FAQ 话术里），不存在从检测框序列到动作结论的算法链。

## 出手人/球员/动作相关能力（对我们痛点②的价值）

- 有 player 类检测（野球场小目标人框），但无人 Re-ID、无跟踪、无「谁出的手」逻辑。
- 「shoot 类别框标在正在投篮的人身上」这一标注思路，理论上可给「出手时刻+出手人候选框」提供弱信号——但此仓库无代码无权重，价值只在思路层面。

## 声称的指标

mAP@0.5 = 0.913（另一处 92.6%）、70 FPS（另一处 65 FPS）、45.3M 参数；分类别 F1：球员 0.920 / 篮筐 0.914 / 篮球 0.884；动作分类 F1 平均 0.889。数字前后矛盾、无实验证据链，应视为虚构。

## 对我们项目的可借鉴点（结合两大痛点逐条说）

1. 痛点①：**最有价值的发现是数据线索而非代码**——Roboflow Universe 存在一族「野球场 + ball/rim/player/ref + made/shoot 类别」的公开小数据集（本库 714 张这套；搜索还见 test-datset/player_detect（6 类含 made/shoot）、sky-long-ai/shot_detection（FG Attempt/FG Made/Hoop）、FirstTime「Basketball Game Detections」8.45k 张含 FG Made/Hoop/Player/Ref 等）。CC BY 4.0 可白嫖，可作我们球/筐检测器的预训练/域适应起点，省标注。
2. 痛点②：确认了「动作即类别」的偷懒路线在野球场数据上已有人标注（shoot 框=人+球动作瞬间），若我们日后做「出手帧检测」可顺着这族数据集找现成标注；但它只给「有人投篮」，不给「是谁」，对归人帮助有限。
3. VanillaNet 轻量化方向对我们无意义（我们不需要边缘部署，需要的是小目标召回）。

## 明确不适用的点及原因

- 零代码零权重，所谓「改进」无法复现，指标不可信，无任何工程可抄。
- 714 张规模太小，只配当预训练种子或域适应源，撑不起独立训练集；且其「made」类是结果框不是轨迹判据，与我们「穿越筐口平面几何」的判定哲学不同源。
