## 1. 背景与目标

用户每周打篮球，用**三脚架固定机位**录制半场单篮筐的整场视频（单个长视频，30 分钟至 2 小时）。希望有一个工具自动检测进球并合成一个集锦视频。

### 已确认的需求

| 项 | 决定 |
|---|---|
| 拍摄条件 | 三脚架固定机位、高角度俯拍、半场单篮筐、篮筐区域始终清晰无遮挡 |
| 球场 | 固定球场固定机位（标定一次即可复用） |
| 干扰因素 | 球员衣服以黑白为主，极少橙色（颜色分割干扰小） |
| 输入 | 单个长视频（30 分钟 - 2 小时） |
| 输出 | 一个合成集锦 MP4；各进球的单独特写片段顺带保留 |
| 准确度取舍 | 宁多勿漏；不确定片段标记出来，由用户在界面人工确认 |
| 使用方式 | 图形界面（Gradio 浏览器界面） |
| 硬件 | 有 NVIDIA RTX 3050 (4GB)，但本方案不依赖 GPU |
| 剪辑时间 | 默认进球前 15 秒、后 5 秒；支持全局默认 + 单片段微调 |
| 验收门 | 样本片段漏检 ≤15% 且误报不淹没待确认列表 |

## 2. 技术方案选型

### 结论：方案 A（传统视觉 OpenCV），预留方案 B（YOLO）升级路径

评估过的方案：

- **方案 A：传统视觉（颜色分割 + 位置规则）** — 选定。用户视频条件（高角度无遮挡、黑白衣服、固定球场固定机位）消解了该路线的经典弱点（遮挡、颜色干扰、重复标定）。成本低（安装约 300MB、无 GPU、处理速度数倍实时）。剩余风险：篮筐自身橙红色（用标定掩膜解决）、运动模糊（判定只依赖位置不依赖形状）
- **方案 B：YOLO 检测 + 轨迹规则** — 升级备选。若验收门不达标，仅替换"找球"的检测层为 YOLO，筐口定位、判定、UI、剪辑层全部复用。GitHub 上成功的主流开源实现（avishah3/AI-Basketball-Shot-Detection-Tracker 等）均为该路线，届时可作算法参考（注意其代码无明确开源协议，只参考思路不复制代码）
- **方案 C：端到端行为识别** — 否决（无现成模型、训练成本高）
- **方案 D：音频信号** — 可选辅助，第一版不做
- **方案 E：VLM API 预筛待确认片段** — 可选辅助，第一版不做（避免 API 费用）
- **方案 F：现成产品** — 否决（用户想拥有自己的工具）

### 技术栈

- Python 3.11+ + OpenCV（检测）
- Gradio（浏览器图形界面）
- ffmpeg（切片与拼接，统一转码 H.264 + AAC）
- 不依赖 GPU

## 3. 架构与组件

```
┌─────────────────────────────────────────────────────┐
│                    Gradio 界面层                      │
│   [标定向导]        [视频分析页]        [集锦生成页]   │
└──────┬──────────────────┬──────────────────┬────────┘
       │                  │                  │
       ▼                  ▼                  ▼
 ┌──────────┐      ┌────────────┐     ┌────────────┐
 │ 1.标定模块 │      │ 2.进球检测  │     │ 4.剪辑合成  │
 │ calibration│─┐   │  detector  │ ─┐ │  editor    │
 │ 筐口位置/   │ │   │ 3.进球判定  │  │ │ ffmpeg切片 │
 │ 球色阈值   │ │   │ goal_decider│  │ │ +拼接集锦  │
 └──────────┘ │   └─────┬──────┘  │ └────────────┘
              ▼         ▼         ▼
        calibration.json   events.json
```

五个职责单一的模块，通过落盘的中间文件衔接：

| 模块 | 职责 | 输入 → 输出 |
|---|---|---|
| 1. calibration | 一次性标定：筐口矩形、篮筐掩膜、球 HSV 颜色范围 | 一段视频 + 用户交互 → calibration.json |
| 2. detector | 逐帧（隔帧）在筐口 ROI 内颜色分割找球，流式输出球位置时间序列 | 视频 + calibration → 球位置序列（内存流，不落盘） |
| 3. goal_decider | 纯函数规则判定：位置序列 → 进球事件 + 置信度分层 | 位置序列 → events.json |
| 4. editor | 按勾选与时间窗口 ffmpeg 切片、统一转码、拼接 | events.json + 用户勾选 → highlight.mp4 + clips/*.mp4 |
| 5. GUI (Gradio) | 标定向导、视频分析、事件复核与集锦生成三个页面 | — |

关键设计决定：

- **检测与判定分离**：判定逻辑是纯函数，可独立单元测试；调规则不重跑视频
- **events.json 持久中间层**：改剪辑参数、重新打勾都基于 events.json 重出集锦，不触发重新检测
- **只检测筐口 ROI**：判定不依赖完整轨迹，只需球在筐口附近的状态（从上方下穿筐口平面），将检测范围缩到最小，规避场边偶发橙色物体
- **帧率减半**：每 2 帧处理 1 帧（球穿筐持续 0.3s 以上，30fps 下仍有约 5 个采样点），速度翻倍

## 4. 首次标定流程（一次性）

1. 用户放入任意一段日常视频
2. 向导均匀抽 5 帧，展示第一帧
3. 用户框选篮筐 → 记录筐口矩形（判定基准平面）+ 篮筐掩膜（分割时忽略篮筐自身的橙色）
4. 用户在帧上点击篮球（1-3 次，可跨帧）→ 自动计算球的 HSV 范围（以点击像素为中心向四周放宽余量）
5. 预览验证：显示"分割结果叠加图"（球被高亮、篮筐被掩掉）
6. 用户确认后保存 calibration.json

标定页提供 HSV 阈值滑块手动微调；固定球场固定机位下预期不需要。

## 5. 日常使用流程

1. 放入本周视频 → 后台自动检测+判定（进度条 + 预计剩余时间）→ 生成 events.json
2. 界面呈现事件列表，分两组：**高置信（默认全选）**、**待确认（默认不选，逐个预览打勾）**
3. 预览按当前时间窗口用 ffmpeg 秒级定位流式播放（不预切文件），调整秒数即时生效
4. 两级时间编辑：全局默认（进球前 [15] 秒 / 后 [5] 秒，可一键应用全部）+ 单片段前/后秒数微调
5. 点击"生成集锦" → ffmpeg 切片 → 统一转码拼接 → 输出：
   - `highlight_<日期>.mp4`（集锦）
   - `clips/<时间戳>.mp4`（各进球单独片段，顺带保留）

## 6. 数据流要点

- 单向流水：video → 球位置序列（内存流式）→ events.json → mp4；每步产物落盘可复用
- 检测流式处理：逐帧读、只维护筐口 ROI 附近的滑动窗口状态，内存恒定（数百 MB 级），2 小时视频不撑爆内存

## 7. 错误处理

| 情况 | 处理方式 |
|---|---|
| 视频损坏/无法打开 | 启动时即报错，不进入长流程 |
| 检测中途退出/睡眠 | 每 5 分钟写检查点（已处理时间戳 + 进行中事件状态），重开后续跑 |
| 标定失效（换球场/光线突变/换球） | 统计球检出率，整段几乎找不到球时界面警告建议重新标定，不默默输出空结果 |
| 片段窗口越界（进球在视频头尾附近） | 时间窗口收缩到视频边界内 |
| 两进球间隔小于片段窗口 | 片段自动合并，避免画面重复 |
| ffmpeg 失败 | 显示 stderr 摘要；保留 events.json，剪辑可重试 |
| 无音轨视频 | 兼容，集锦静音生成 |

拼接统一转码 H.264 + AAC（避免不同参数片段直拼花屏），代价是几分钟转码时间，换任何手机可播放的兼容性。

## 8. 判定规则（goal_decider 状态机）

| 场景 | 判定 |
|---|---|
| 球从筐口上方下穿筐口平面，水平位置在筐口内 | ✅ 进球候选 |
| 打铁后球从筐口下方向上穿过（弹框） | ❌ 不触发（要求方向向下） |
| 空气球 | ❌ 不触发 |
| 球在筐附近被拍/运球经过（无下穿） | ❌ 不触发 |
| 球下穿但位置数据残缺（零星几帧） | ⚠️ 低置信 → 待确认，用户裁决 |
| 篮网摆动信号 | 仅作加分项提高置信度，非必要条件（避免篮网被挡时漏检） |

置信度分层：高于高阈值 → 高置信组；中间地带 → 待确认组；低于低阈值 → 丢弃。满足"宁多勿漏"：高/待确认之外的才丢弃，人工复核兜底误报。

## 9. 测试策略

1. **单元测试（判定逻辑，主战场）**：goal_decider 纯函数，用合成位置序列穷举——标准进球、打铁、弹框、空气球、噪声点、残缺轨迹等十几种序列，断言判定与置信度分层
2. **单元测试（标定与分割）**：从样本视频抽帧做固定测试图，验证颜色分割稳定框出球
3. **集成验收（验收门）**：从样本视频挑 2-3 个各 10 分钟片段，用户人工标注真实进球时间点（一次性约半小时）；跑完整管线产出报告：漏检 X / 误报 Y / 待确认 Z。通过标准：漏检 ≤15% 且误报不淹没待确认列表；不达标则启动 YOLO 升级路径
4. **回归测试**：每次调判定规则后重跑集成验收

## 10. 升级路径（方案 B 备选）

若验收门不达标：仅替换模块 2（detector）的"找球"实现为 YOLO（ultralytics，RTX 3050 可跑），calibration / goal_decider / editor / GUI 及 events.json 接口全部不变。检测权重优先试公开预训练，不足则用公开数据集（Roboflow）在本地微调；算法可参考 avishah3 项目的思路（不复制其代码）。
