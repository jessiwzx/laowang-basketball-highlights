# 方案：剪辑台预览叠加「出手→进球」全弧轨迹（评估稿，未动代码）

- 日期：2026-10-15
- 状态：**待用户确认后开发**（按用户 2026-10-15 定的规矩：改代码前先出方案）
- 目标效果（用户原话）：**「从出手到进球一个完整的标记」**，加在**剪辑台预览视频**上；**输出视频暂时不加**（未来可能加）。

---

## 0. 结论先行（三句话）

1. **能做，且是"新增一段算力 + 一层前端叠加"，不是改造现有管线**——不动检测主管线、不动判定、不动出片、不动 shooter。
2. **耗时已实测**（本机 RTX 3050 Laptop GPU）：全帧检球 **13 ms/帧（≈2.5x 实时）**；**单颗球约 0.5 秒**（只算飞行窗），**整场 254 球约 2~10 分钟**（取决于窗口取多长），**按需只算你看的那一颗则首次 0.5~2.4 秒、之后走缓存≈0**。
3. **主要不确定性不在耗时，在"弧的准确性"**：4 颗球小测里，链能覆盖飞行段的 36%~93%，**1/4 明显不可用**。所以方案必须带一道**"质量门"**：过门才画弧，不过门就不画（而不是画一条错的）。
4. **交互形态（用户已定）**：页面上做成**开关**，**默认关**；**只在打开时才按需计算**（关=零成本，开=只为当前这一颗付 0.5~2.4 s，之后走缓存）。见 §6。

## 1. 数据从哪来（三条路线，成本差 100 倍）

| 路线 | 数据源 | 能否出全弧 | 边际计算成本 | 代价/风险 |
|---|---|---|---|---|
| **① 复用现有溯源链** | `shooter.py` 运行时算的 `chrono` 链 | ✅（本就有 release→goal 的链） | **≈0**（已经算过，只是没存） | **要改 `bbh/shooter.py`** → ⚠️ **与另一会话正在做的溯源改动撞车**；且它是 HSV 链，质量≈现 GIF 里的跟球十字（你反馈过"十字不准"） |
| **② 独立全帧检球（推荐）** | 新增只读模块跑自训 `best.pt` 全帧检球 | ✅ | 见 §2（单球 0.5~2.4s） | **不碰 shooter、零依赖**（ultralytics 已在环境里）；弧质量需过质量门 |
| **③ 只用 `positions.json`** | 主管线已落盘的坐标 | ❌ **画不出** | 0 | 主检测只覆盖**筐口 ROI（画面 3.6%~6.4%）**，6 秒窗内球只被检到 0.67s → **不成弧**。**此路排除。** |

> **路线①的陷阱**：看似免费，但它把"预览叠加"和"另一会话正在改的 shooter"绑在一起。**除非你要接管那条线，否则不建议**。
> 所以下面全部按 **路线②** 估成本。

## 2. 耗时实测（这是你要的核心数字）

环境：本机 `RTX 3050 Laptop GPU` + torch 2.5.1+cu121 + ultralytics 8.4.163；视频 1280×720@30fps。

| 环节 | 实测 | 折算 |
|---|---|---|
| 解码（光读帧） | **1.4 ms/帧** | 43x 实时 |
| HSV 全帧检球 | **2.5 ms/帧** | 12x 实时 |
| **YOLO 全帧检球（imgsz=1024）** | **13 ms/帧** | **2.5x 实时** |
| YOLO 全帧（imgsz=640） | 12 ms/帧 | 无明显收益 |
| YOLO 批量 32 帧一批 | 9.7 ms/帧 | 仅省 ~25%（GPU 太小，瓶颈是单次调用开销） |

**按窗口长度折算（单颗球）：**

| 窗口 | 帧数 | 耗时 |
|---|---|---|
| **飞行窗（出手→进球，实测 0.83~1.13s）** | ~36 | **≈0.5 s** |
| 现有回扫窗（6s） | 181 | **≈2.4 s** |

**按场次折算**（以 `2025-06-28_1` 为例：**254 个进球事件**）：

| 策略 | 增量耗时 |
|---|---|
| **按需计算**（只算你打开预览的那颗，带缓存） | 首次 **0.5~2.4 s**，二次 **≈0** |
| 预计算·只算飞行窗 | 254 × 0.5s ≈ **2.1 分钟** |
| 预计算·6s 回扫窗（与现有溯源同窗） | 254 × 2.4s ≈ **10 分钟** |

**前端叠加本身**：canvas 画 30~60 个点 = **<1 ms/帧**，**可忽略**（不重编码、不重切视频）。

> 判定：**若不预计算，耗时几乎无感**（只在首次打开某球时多等半秒到两秒，之后缓存）。**若预计算**，代价是每场视频的流水线多跑 **2~10 分钟**——**这是你决定"做不做"的唯一数量级问题**。

## 3. 逻辑成本（改哪些文件、多大改动）

| 层 | 改动 | 规模 | 风险 |
|---|---|---|---|
| 新模块 | `bbh/ball_arc.py`：对指定进球跑全帧检球 → 建链 → 质量门 → 缓存 | ~150-200 行 | 低（独立新文件，不改现有行为） |
| 缓存 | `work/<视频>/ball_arc.json`（每球 30~60 点；整场约几百 KB） | — | 低（可随时删，自动重算） |
| 后端只读接口 | `bbh/web/` 加 1 个 GET（按 video+t 返回折线与缩放参数） | ~40 行 | 低（只读） |
| 前端 | `frontend/src/edit/ClipPanel.vue`：`.videobox` 内加一层 `<canvas>`，`@timeupdate`/`rAF` 同步画"已播放到"的轨迹 + 一个开关 | ~80-120 行 | 低（纯显示，失败不影响播放） |
| **不动的** | 检测主管线 / 判定（v18 口径）/ shooter / 出片导出 | 0 | — |

**验收方式**：① 20 颗球对拍——链首 vs 现有 `release_xy` 偏差、弧尾是否落到筐口；② 目视 3~5 段预览，确认"球轨迹与画面严丝合缝"（坐标换算 + 时间对齐误差 ≤1 帧）。

**可回退性**：新增文件 + 一个开关，删掉即恢复原状；不动任何既有数据格式。

## 4. 弧的质量：唯一实质风险（已量化）

4 颗球链重建小测（自训 `best.pt` 全帧，conf≥0.05，imgsz=1024）：

| 进球 t | 与现有出手点差 | 链长 | 跨度 | 链尾距筐 | 覆盖飞行段 |
|---|---|---|---|---|---|
| 458.2 | 1.13 s | 14 | 0.47 s | 43.7 px | **93.3%** |
| 473.7 | 1.00 s | 14 | 1.27 s | **157.3 px** | **35.9%** ← 差 |
| 577.0 | 0.83 s | 14 | 0.57 s | 77.5 px | 77.8% |
| 599.4 | 0.83 s | 30 | 1.10 s | 21.7 px | 88.2% |

**读法**：3/4 基本可用，1/4 明显不行（链尾离筐 157px、只覆盖 1/3 飞行段）。原因：远景小球仍有候选歧义（同窗口可能不止一条弧）+ 静态误检。

**因此方案必须带质量门**（建议判据，任一不过即**不画**）：
- 链尾到筐口距离 ≤ 1.5×筐宽；
- 覆盖飞行段 ≥ 60%；
- 二次拟合 R² ≥ 阈值（抛物线形态）且下落段存在。

**顺带的好处**：现有 `release_xy` / `release_t`（已算好、且验收过）可作为**链的种子与校核点**——提高稳健性，**且不增加算力**。

## 5. GitHub 现成实现（按你的要求先搜过）

**同类项目（球轨迹叠加）**

- `mpJunot/ShotPrediction`——YOLOv8（球/筐/人）+ 物理轨迹预测 + Streamlit 网页叠加。**技术栈与我们最像**（ultralytics）。
- `Maseeek/BasketballAnalysis`——Hough 圆 + 二次多项式拟合 + **轨迹拖尾叠加**（`findBall` + `polyfit`）。
- `thrishi0610/Basketball_shot_predictor`——HSV + 二次拟合 + 叠加输出。
- `lfahmy/trajectory`——背景差分 + "已走过轨迹 + 预测轨迹"双色叠加。
- `AniT20EXPERT/Smart-Shot-Analyzer`——**R² 阈值判"擦筐/进筐"**，可作我们的质量门思路。

**前端叠加（路线 A 的架构参考，重点看这几个）**
- `bryanlje/mds06-frontend`（羽毛球）——**后端出 JSON、前端在播放器上叠框与标注并与事件日志同步、点事件跳时间戳**。这就是"预览叠加"的标准做法。
- `Sherin-SEF-AI/Sports-analytics`——Flask + React + **Canvas API 视频叠加**。

**说明**：我们此前的竞品调研覆盖的是"检测/跟踪/归人"，**没有覆盖"轨迹叠加渲染"这一块**——上面这批是本次新补的。

## 6. 交互形态：页面开关 + 按需计算（2026-10-15 用户已定）

**决定**：这个功能在页面上做成**开关**；因为单球计算耗时相对明显，**只在开关打开时才计算/绘制**——有需要才输出。

**交互设计**
- **位置**：剪辑台预览面板（`ClipPanel.vue` 的 `.videobox` 上沿）加一个 **「轨迹」开关**，**默认关**。
- **开** → 前端请求只读接口；**无缓存则现算**（首次 0.5~2.4 s，显示加载态，避免误以为卡住）；有缓存立即返回。
- **关** → 不请求、不计算、不绘制，**零开销**（无算力 / 无磁盘 / 无网络）。
- **缓存**：`work/<视频>/ball_arc.json`，按球（键=时间）存；删掉即重算；同一颗球第二次打开**瞬时**。
- **可选增强（后续）**：加一个「预计算本场」按钮，把 §2 里那 2~10 分钟一次性跑掉，之后全瞬时。

**为什么这样最省**
- 关态：整条链路**零成本**。
- 开态：只为**你真看的那一颗**付 0.5~2.4 s；看过即缓存，重复看 = 0。
- 只有"把全场 254 球都开着看一遍"才等于场次预计算的成本（2~10 分钟），而这由你主动控制。

**与质量门配合**：算完但**不过质量门**的球 → 返回"无弧"标记，界面显示"本球无可信轨迹"，**而不是画一条错的**。

## 7. 建议方案（分两步，第一步就能决定做不做）

**第一步 · 先做"能不能稳定出弧"的小样本对拍（只读，不改任何产品代码）**
- 取 30~50 颗球（含各类机位/光照），跑全帧检球 → 建链 → 过质量门；
- 输出：**过门率**（预计 60%~85%）、单球平均耗时、坐标/时间对齐误差；
- **产出物**：一份结论 + 3~5 段叠加样张（图片/短视频）给你看。
- **这一步的代价：约半小时机器时间，零代码风险。** 过门率不理想 → 直接停，不进入第二步。

**第二步 · 落地"预览叠加"（按你的选择做）**
- **交互（已定）**：页面**开关**，默认关，**开启才按需计算**（见 §6）；
- 推荐形态：**静态全弧**（一条折线 + 拖尾点 + 筐口框 + 进球竖线），可选"随播放逐段长出"；
- 计算策略（已定）：**按需 + 缓存**为主，可选加「预计算本场」按钮；
- **输出视频叠加（路线 B / 烙进片子）本轮不做**，留作后续可选项。
