## 0 一句话结论

它的**判定链精度不如我们深，但有两个设计比我们先进**：① **按视频切换判据而非调阈值**（`apply_video_occlusion`）；② **网运动的相对量测量**（事后 top5 − 事前中位数）。这两条直指我们「网分线结案」的那个死结，值得重测。

工程侧最值得抄的是 `check_runtime.py`（一键环境自检）和缓存 key 的完整度——**开源后朋友装不上，比精度低更要命**。

## 1 它的系统全景

```
代理视频(960×720/5FPS) → 粗扫(scale=4,batch=8,conf=0.10)
   → 精筛 原视频 ±2.5s 窗 / 10FPS / scale=2  → find_refined_crossings
   → 逐帧复核 原视频 ±1s / 30fps / 筐周 5 倍筐宽方形 crop → assess_rim_crossing
   → status ∈ {made, rejected, unsure, skipped} → 人工审核 → 导出
```

关键模块（都在 `src/basketball_highlight/`）：

| 模块 | 作用 |
|---|---|
| `events.py` | `find_refined_crossings`、`calibrated_gates` / `normalized_calibrated_gates` |
| `rim_check.py` | **判定核心** `assess_rim_crossing`、`keep_unless_seen`、`apply_video_occlusion` |
| `net_motion.py` | `net_motion_series`、`motion_box`、`prepare` |
| `tracking.py` | `link_ball_detections` |
| `ranking.py` | `dedupe_candidates` |
| `inference.py` | 设备选择 cuda>dml>coreml>mps>cpu；DirectML 走 ORT，其余 ultralytics |
| `roi.py` | `effective_crop_scale` |

它的判定链（`rim_check.py` docstring 原文，5 条必过）：

1. 从筐口**上方下落**（`entry`：穿越前 15 帧内存在 −1.2 ≤ y ≤ −0.1 的点）
2. **在筐内穿过筐平面**（`|x_cross| ≤ 0.7`，注释：筐口跨 ±0.5，**滚筐可达 0.7**）
3. **落到底部且靠近筐心继续下落**（`reached_net_bottom`：30 帧内 y ≥ 1.0；`|x_exit| ≤ 0.7`）
4. **不在筐附近反弹**（`rebound`：y 回升 > 0.3）
5. **穿筐/穿网时至少一帧被遮挡或模糊**（`hidden_frames ≥ 1`，conf < 0.5 记为看不见）

坐标全部**按筐宽归一化**：`x=(x−center_x)/width`，`y=(y−rim_y)/width`。

常量（全部带实测注释）：

```python
MIN_RIM_WIDTH_PX = 30.0      # 筐小于 30px 直接 skipped，留人工
CROP_RIM_WIDTHS = 5.0        # 方形 crop 边长 = 5 倍筐宽
WINDOW_BEFORE_S = WINDOW_AFTER_S = 1.0
MIN_BALL_CONF = 0.15 ; STRONG_BALL_CONF = 0.5
MAX_CROSS_OFFSET = 0.7 ; MAX_EXIT_OFFSET = 0.7 ; MIN_HIDDEN_FRAMES = 1
MIN_OCCLUDED_SHARE = 0.5 ; MIN_OCCLUSION_SAMPLES = 8 ; STRONG_OCCLUDED_SHARE = 0.8
MIN_NET_MOTION = 0.0
MIN_OFF_CENTER_TRACK_POINTS = 10 ; MIN_OFF_CENTER_TRACK_SPAN = 1.0
_ZONE_X = 2.5 ; _ZONE_TOP = -2.5 ; _ZONE_BOTTOM = 3.0
```

## 2 A 档：建议认真考虑（高价值 / 可落地）

### A1 ★ 按视频切换判据，而不是弃权或调阈值

**它的做法**（`apply_video_occlusion`，docstring 原文）：

> Drop the occlusion rule for a video whose net does not hide the ball. Close, low cameras with a thin net see the ball clearly through the net, so this rule is dropped for a video where most central crossings stay visible. Such a video instead needs the net to move after the crossing.

逻辑：

```python
central = [c for c in results if 通过除遮挡外全部规则]     # 中心穿越
share = 靠"遮挡"通过的比例
use_rule = len(central) < 8 or share >= 0.5               # 该视频的网遮不遮球
# 不用遮挡规则时 → 改判"网是否移动"（net_motion < 0 即判未进）
```

注释给的实测：有网遮的场次 86% / 95% / 70% 的中心穿越被遮挡；**近距离细网只有 16%**。

**为什么这条对我们重要**：我们「网分线结案」的结论是「弱场无解、只能人工补勾」。它提供了**第三条路**——不是改 `NET_STATIC_TH`，也不是弃权，而是**换一个判据顶上**。

而且它的判据量（`share` = 遮挡通过率）和我们试过的「全场 post 分布」是**完全不同的可观测量**。我们的实测是「全场 post 分布判不出弱场」，但这不能推出「遮挡通过率也判不出」——**这是尚未测过的方向**。

> 待验证：用现有 18 场的 positions 数据能否复算出「中心穿越里靠遮挡通过的比例」，并检查它是否与「网分 AUC」负相关。

### A2 ★ 网分改成相对量（事后 − 事前），而不是绝对阈值

它的测量（`net_motion_score`）：

```python
before = series[cross_frame-24 : cross_frame-5]        # 穿越前 19 帧
after  = sorted(series[cross_frame+1 : cross_frame+21]) # 穿越后 20 帧
return mean(after[-5:]) - median(before)                # 后段最大5帧均值 − 前段中位数
```

阈值 `MIN_NET_MOTION = 0.0` —— **几乎就是「只要比之前动就算动」**。

**对比我们**：`NET_STATIC_TH = 5.0` 是**绝对帧差**，而实测真球 `net_post` 中位数跨场差 4.4 倍（10-23 的 2.98 vs 11-06 的 13.18）——绝对阈值天生无法跨场。

它的相对量理论上能消掉场次偏置。**这可能是「弱场网分 AUC < 0.5」的真正解法。**

但有一个重要前提：**它敢用 0.0 是因为还有「遮挡规则」兜底**（A1）。我们没有遮挡规则，直接照抄 0.0 会放进来一堆假绿。所以 A1 与 A2 是**一组**，要一起测。

> 注意：这和我们已否掉的「全曲线取峰」不是一回事——那次实验仍是绝对阈值 + 取最大，被假绿同幅抬高打死。相对量是不同的问题。

### A3 ★ 把球从网区 mask 里挖掉

```python
MASK_BALL_CONF = 0.3 ; MASK_PAD = 0.2   # 单位：筐宽
for detections in frames[index-1 : index+1]:
    mask[球框外扩 0.2W] = False          # 球本身不算"网在动"
if mask.sum() <= 50: series.append(None) # 网区被球盖完 → 本帧无效
```

**我们的网区测量有没有排除球本身？** 如果没有，真球穿网时球就在网区里，帧差里混着球自己的位移——**真球和假绿都会被抬高**，这正是我们观察到的「假绿同幅抬高」现象的可能来源之一。

这是**最低成本、最可能立刻见效**的一条。可在离线数据上直接复算验证（不需要重跑检测，positions 里已有球框面积）。

### A4 「只在看见了才排除」——按证据类型决定能否降级

```python
UNSEEN_REASONS = ("no_crossing", "no_entry", "no_exit")   # 都是"没看见"
def keep_unless_seen(result, refined):
    if reason in UNSEEN_REASONS:  proven = (not refined) and (not ball_approached)
    elif reason == "off_center":  proven = track_points >= 10 and track_span >= 1.0
    elif reason == "not_occluded": proven = occluded_share >= 0.8
    else: proven = True
    return result if proven else {**result, "status": "unsure"}
```

**要点：不是所有拒绝理由都同等可信。** `off_center` 要 ≥10 个轨迹点且跨度 ≥1.0 筐宽才敢断言（注释：假绿的「球衣在旁边」轨迹只有 0.45 筐宽）；`not_occluded` 要全场遮挡率 ≥0.8 才敢用。

**对我们**：我们的 `review_reason`（area / entity / geom / 孔洞）目前是「命中即降级」，没有区分「这个理由的证明强度够不够」。可以给每个 reason 配一个最小证据门槛——**这属于门禁范式里的「护栏」层，符合既有规矩**。

### A5 滚筐球要算进

```python
# The rim opening spans +-0.5; a ball rolling on the rim crosses up to 0.7.
MAX_CROSS_OFFSET = 0.7
```

筐口名义跨 ±0.5，**滚筐会到 0.7**，所以门限放宽到 0.7。

**我们的 `CROSS_KILL_OFF` 是多少？** 如果沿用 0.5 上下的口径，**滚筐进球可能被几何门杀掉**。这是个便宜的检查项——`feedback.json` 里应该有「用户标了 goal 但我们判 off_center」的样本，可直接查。

### A6 `check_runtime.py` —— 一键环境自检

一条命令输出：

```
runtime: OK
- engine: OK / src: OK / sqlite_schema: OK / scripts: OK
- model: OK / python_imports: OK / ffmpeg: OK / ffprobe: OK
```

明确写着「**只检查环境完整性，不验证模型准确率**」。

**这是开源项目最该抄的一个文件。** 朋友装不上时，让他跑一条命令把结果贴回来，比来回问十句有用。我们现在的失败模式是「.bat 黑框一闪就没了，用户不知道哪一步错」。

### A7 缓存 key 的完整度 + Windows MAX_PATH

```python
DETECTION_CACHE_VERSION = "python-v2.5-white-net-region"
ALGORITHM_VERSION       = "python-v2.15-crop-scale-clamp"
REFINED_SCHEMA_VERSION  = 3
signal_version          = 4     # 也在 cache key 里
```

缓存 key 包含：视频指纹(size+mtime) + 模型指纹 + roi + time + window + sample_fps + scale + crop_scale + conf + batch + rim + net_roi + signal_version。

两个细节值得抄：
- **算法版本与检测缓存版本分离** → 改判定不用重跑检测（这正是我们 L0/L1 的分层，但它的缓存粒度更细）
- **文件名用 sha256 前 24 位**，注释写明「避免 Windows MAX_PATH 超限」→ 我们在 Windows 上迟早踩

### A8 `check_open_source.py` —— 扫仓库别把不该提交的东西提交了

我们开源前应当有一个等价物：扫 `work/`、`*.mp4`、`calibration.json`、`feedback.json`、`*.pt`（非 `bbh/weights/`）是否被意外追踪。这是**一次性的保险**，成本一小时。

## 3 B 档：思路可取，但要么成本高、要么方向不对

| 点 | 它的做法 | 对我们的判断 |
|---|---|---|
| 分层性能架构 | 代理 960×720/5FPS → 粗扫 → 原视频精筛 | 我们整帧 1024 逐帧跑，简单但慢。**若要让朋友在 CPU 上可用，这是必经之路**；但会动到主链路，风险大 |
| 设备后端抽象 | cuda>dml>coreml>mps>cpu，按设备自适应 batch（CPU=8 因 16 张慢 5 倍；DML=1 因 dynamic shape 退化） | 我们有 CUDA 就够；**要支持 Windows 集显/CPU 时才需要**。注释里写实测依据的做法值得学 |
| 引擎/UI 协议分离 | Flutter ↔ Python 走 JSONL，SQLite 存状态 | 我们 FastAPI+Vue 已等价，**不必改** |
| 音频特征 | `extract_audio_features.py` | 我们已证伪 4 个物理证据，音频是新模态但噪声/解说干扰大，**不建议投入** |
| 框图→自动 ROI | `detect_auto_roi.py` | 我们靠人手标定，这是「少点几下鼠标」的优化，**不解决精度** |

## 5 明确不建议照抄

1. **`MIN_NET_MOTION = 0.0`** —— 它敢这么松是因为有遮挡规则兜底。**单独照搬会放进大量假绿。**
2. **简单贪心跟踪**（`max_gap=12` 帧、`max_jump=2.0`、每帧 0.7 筐宽）—— 我们 v20 的冷却身份判据（`_new_ball_since`）比这精细，别退回去。
3. **把手写门限换成训练分类器**（`train_classifier_cv.py`）—— 我们 R-020 已证 3744 组白名单族七门全过 0 组，加分类器只是过拟合开发集。
4. **Flutter / Rust / ONNX 多后端** —— 对它必要（要上手机），对我们纯增成本。
5. **scripts 与 src 两代并存**（`refine_candidates.py` 与 `refine_dynamic_candidates.py`）—— 这是它的技术债，别学。

## 6 若要落地，建议顺序（每步都要先出方案再动手）

| 步 | 内容 | 成本 | 验收 |
|---|---|---|---|
| 1 | **A6 `check_runtime.py`**（纯新增文件，零风险） | 1~2h | 干净目录跑出 8 项 OK |
| 2 | **A8 `check_open_source.py`**（纯新增文件） | 1h | 扫出 0 条误提交 |
| 3 | **A5 滚筐口径核查**（只读 `feedback.json` + events） | 1h | 列出「用户标 goal 但被 off_center 杀」的条数 |
